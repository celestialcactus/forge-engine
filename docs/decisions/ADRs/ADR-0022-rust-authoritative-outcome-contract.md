# ADR-0022: Rust-authoritative outcome contracts

- **Status:** Accepted for CLI ship lane 4; implementation awaiting hosted and VS Code gates
- **Date:** 2026-08-04
- **Scope:** Canonical run contract, developer capability pack, host projections

## Context

A provider can produce a schema-valid terminal answer before it has gathered the
evidence required by the developer's task. Forge previously recorded that run as
`completed`, which was mechanically correct but easy for a host or developer to
misread as proof that the objective was achieved. Prompt wording and model
self-assessment cannot close this gap reliably, especially on small local models.

Outcome acceptance belongs beside policy, budgets, event ordering, and terminal
artifact construction in the Rust kernel. Putting it in the CLI, MCP adapter, or a
provider-specific planner would create competing meanings of success.

## Decision

1. `RunStatus` continues to describe lifecycle state. `completed` means the planner
   reached a valid terminal turn; it does not mean the requested outcome is true.
2. Every `RunArtifact` schema version 2 contains an `OutcomeAssessment` with one of
   `not_evaluated`, `verified`, or `unmet`.
3. A caller may supply a bounded, versioned `OutcomeContract`. Rust validates the
   contract before planning and fails with `invalid_outcome_contract` when it is
   malformed.
4. V1 supports three deterministic requirement kinds:
   - `output_non_empty`;
   - exact caller-supplied `output_equals`;
   - `capability_succeeded` for a named capability and minimum invocation count.
5. Rust evaluates the contract after the terminal planner output and emits
   `outcome.assessed` immediately before `run.completed`.
6. No contract produces `not_evaluated`, never implicit verification. A failed
   requirement produces `unmet` while lifecycle status remains `completed`.
7. `verified` means only that every recorded contract requirement passed. It is not
   proof that every sentence generated by a model is factually correct.
8. Capability success is credited only to the requested capability and call ID.
   A result carrying another call ID is normalized to an explicit failed result.
9. The authoritative artifact retains the full contract for audit and replay.
   Compact MCP presentation exposes the assessment but omits the contract to avoid
   duplicating bounded expected-output text in host context.
10. The TypeScript conformance runtime mirrors the behavior for differential tests;
    it remains non-product authority.

## Bounds

- contract schema version: exactly 1;
- requirements: 1 through 32;
- unique, non-blank requirement IDs: at most 100 characters;
- expected output: at most 65,536 characters;
- capability ID: non-blank and at most 200 characters;
- minimum successful invocations: 1 through 64.

## Initial product behavior

The deterministic single-capability workspace service supplies a contract requiring
one successful invocation of the selected capability and non-empty output. Those
read-only CLI and MCP calls can therefore report `verified` within that narrow
meaning. Free-form inference runs do not invent an objective contract and currently
report `not_evaluated`. Later edit/test workflows must construct explicit contracts
from the requested operation and verifier plan rather than model prose.

One-shot CLI execution exits nonzero for `unmet`. Interactive `/status`, human run
summaries, JSON artifacts, and MCP projections expose lifecycle and outcome as
separate fields.

## Consequences

- Early-stopping models can no longer borrow the word `completed` as evidence that
  a requested workflow finished.
- Small local models benefit because correctness does not depend on self-grading.
- Hosts can set stronger task-specific contracts without becoming Forge's runtime
  authority.
- The first contract vocabulary is intentionally narrow. Semantic answer scoring,
  test-result requirements, patch acceptance, and composite workflow objectives
  require later typed requirements and adversarial gates.
- Run artifact schema 1 and bridge protocol v3 peers fail closed against this
  boundary; the accepted versions are RunArtifact v2 and
  `forge.kernel.bridge.v4`.

## Rejected alternatives

- **Treat terminal text as success.** This reproduced false completion.
- **Ask the same model whether it succeeded.** This is self-certification, not
  independent evidence.
- **Infer contracts from arbitrary prompts inside Rust.** That would require a
  second semantic planner and introduce ambiguity into the kernel.
- **Mark the lifecycle failed whenever a contract is unmet.** That destroys useful
  evidence that the runtime and provider completed normally; lifecycle and outcome
  are separate facts.
- **Return the full contract through compact MCP results.** The authoritative
  artifact already retains it, while host context should receive the bounded
  assessment needed for orchestration.
